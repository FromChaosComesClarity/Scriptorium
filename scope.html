Scope report 9 September 2026 LatteWrite 0.7.1 → Scriptorium

Scriptorium

A visual Markdown editor over Simplenote, built on the Tiptap core LatteWrite already ships. Can it be done, what gets reused, and the one thing that will actually hurt.

The call

Fork LatteWrite. Keep the shell, the toolbar and the whole theming engine; replace the document model.

LatteWrite gives you roughly 80% of a beautiful Markdown editor that already exists, is yours, is GPL-3.0, and already runs on Linux and in a browser. What it does not give you is a Markdown document model, and that is the entire job, because a Simplenote note is a Markdown string. Budget the work there, not on the UI.

I

What I actually checked

Every line below was run on this machine today, not recalled. Two results changed the design.

api.simperium.com
Alive

Returns HTTP/2 401 from nginx for /1/chalk-bump-f49/note/index with a bogus token. The Simplenote sync backend is up and answering for the Simplenote app ID. This is the thing that has to work, and it does.

auth.simperium.com
No TCP listener

DNS resolves to 192.0.84.248, but port 443 and port 80 both time out at 25s. Confirmed twice: once sandboxed, once with the sandbox off, at your authorization. The classic username/password login route that every third-party client used is gone. This is the single biggest finding in the report.

simperium.com/1/…
Not an API

Connects in 0.46s but returns a plain nginx 403 whether or not the API key header is sent. That is the marketing site refusing an unknown path, not a relocated auth endpoint. Dead end, ruled out.

app.simplenote.com
Live, but gated

Redirects to /login/, serves a server-rendered page carrying recaptcha/enterprise.js. Login works, but only for a human in a real browser window. No script will ever post credentials to it. This constrains the auth design rather than blocking it.

simperium (npm)
Available, unmaintained

v1.1.4, last published 26 June 2022. The official Node client: WebSocket sync, buckets, change versions, diff-match-patch merge. Four years stale, but the protocol it speaks is the one the live server still answers. Usable; pin it and expect to read its source.

Markdown importer
Does not exist

Grepped LatteWrite for markdown-it, marked, remark, commonmark, micromark, mdast. Nothing. Only turndown, used once, in src/main/export.js:45, one-way HTML to MD. LatteWrite can write Markdown out. It has never had to read Markdown in. Section III is about this.

Chromium token
Blocked, and unnecessary

Reading your Chromium profile was refused by the permission classifier, its standard guard on browser credential stores. No workaround needed. The correct design has Scriptorium log in through its own window and read its own session, so nothing is ever lifted out of another browser.

II

What LatteWrite hands you for free

LatteWrite 0.7.1 is Electron + electron-vite + Svelte 4 with a Tiptap 2 core, GPL-3.0-or-later, about 5,300 lines across src/ and web/. It already builds an AppImage and a PWA from one codebase, and the PWA imports the desktop app's extension modules directly so both share one ProseMirror schema. That discipline is exactly what makes it forkable.

The theming engine is the answer to "can we skin it"

Yes, comprehensively. A LatteWrite style is a plain object: bg, surface, text, muted, accent, selection, caret, rule, a font trio, a measure, all applied by setting CSS variables. There is already a data-skin hook that repaints the whole shell to portray a vintage OS, and bundled bitmap fonts (C64, IBM VGA, Chicago) to go with it. Mapping an Omarchy theme onto that object is a small function, not a project, and it means Scriptorium can follow your system theme automatically and carry its own.

Dictation is an unexpected bonus: src/main/dictate.js already speaks to LatteDictate on port 42815 and honours the ?type=off contract, so Ctrl+D dictation into notes costs you nothing but the copied file.

III

The hard problem, stated honestly

LatteWrite's document is Tiptap JSON in a zip. A Simplenote note is a single Markdown string in a content field. Scriptorium must convert Markdown → Tiptap on every note open, and Tiptap → Markdown on every keystroke-triggered save, and that round trip has to be stable. An unstable one does not merely look wrong, it writes the damage back to your account and syncs it to your phone.

Two distinct pieces of work fall out of that:

1. Build the importer that has never existed

Tiptap 2 has no official Markdown serializer. The realistic options are tiptap-markdown (0.9.0, thin and a little abandoned) or wiring ProseMirror's own prosemirror-markdown against the schema, which is more work and far more controllable. Given the round trip has to be lossless, I would write it against prosemirror-markdown with a schema defined to match Simplenote's Markdown dialect, and test it with a corpus of your real notes before it is ever allowed to save.

2. Decide what happens to everything Markdown cannot express

These LatteWrite features have no Markdown representation. If they stay enabled and a note is saved, they are silently destroyed:

  • Text colour, highlight colour, and the textFx glow/neon marks
  • Per-selection font family, and text alignment
  • Image widths, and the borderless-table flag
  • Embedded images generally, because Simplenote stores text and a pasted screenshot has nowhere to live
  • The whole presentation-mode extension

The correct answer is not a warning dialog. It is to remove those extensions from the Scriptorium schema entirely, so the toolbar only ever offers what Markdown can hold: headings, bold, italic, strikethrough, inline code, links, blockquotes, both list types, task lists, code blocks, tables, and horizontal rules. A toolbar that cannot lie is worth more than a richer one that can. Images become a link to a hosted URL, or they are out of scope for v1.

One interop detail worth getting right on day one: Simplenote only renders a note as Markdown when its systemTags array contains markdown. Scriptorium should set that tag on every note it touches, or your notes will look like raw syntax in the official mobile app.

IV

Login, and the host that isn't there

With auth.simperium.com refusing connections, a token has to come from somewhere else. Three routes, and one of them is clearly right.

Ruled out

Post credentials to the auth API

The endpoint every third-party client used. Nothing is listening on either port. Not degraded, absent.

Recommended

Log in in our own window

Open app.simplenote.com in a real Electron window. You type your password; reCAPTCHA sees a genuine browser and is satisfied. We then read the Simperium token out of our own session and hand it to the sync client. Your credentials never touch our code.

Fallback

Paste a token

A settings field taking a token you obtain yourself. Ugly, but it is the escape hatch when the web app's storage shape changes under us, and it costs about twenty lines.

Build both the recommended route and the fallback. The exact storage key the web app uses for the token is the one thing here I could not verify without logging in, so the first hour of that phase is confirming it in a live window. The paste field means a wrong guess is an inconvenience, never a blocker.

V

Wrapping the web app, as you asked

You asked me to check whether wrapping the Simplenote web app is the last resort. It splits into two very different ideas, and separating them is what produced the recommendation above.

Wrapping it as the whole UI: no

This fails on its own terms. Simplenote's web editor is a plain text surface; the visual toolbar you want does not exist in it. Getting one would mean injecting a Tiptap layer over somebody else's React application and re-deriving their DOM after every deploy Automattic ships. It is the fragile option and the one that gives you the least control over skinning, so the two things you asked for are precisely the two things it is worst at.

Wrapping it as a login window: yes, and it rescues the project

The useful half of your instinct. Point a real browser window at their login page for authentication only, then close it and never render it again. That is what defeats both the dead auth host and reCAPTCHA in a single move. So the web app does earn a place in the architecture, as a doorway rather than as the building.

VI

Build order

Sequenced so the riskiest unknown is proven before anything is built on top of it.

  1. Prove the round tripBefore any UI. A standalone script: real notes in, Tiptap JSON, Markdown out, diffed against the original. If this is not clean, nothing downstream matters.
  2. Prove sync read-onlyToken in hand, simperium pinned, pull your note index and one note's content. Confirms the 2022 client still speaks to the 2026 server.
  3. Fork the shellCopy LatteWrite, strip Drive/OneDrive/.latte/presentation, cut the extension list to the Markdown-safe set, rename to Scriptorium.
  4. Wire the note list and editorSidebar of notes, tag filter, search. Autosave debounced into the Simperium bucket, with the markdown system tag set.
  5. Login window and settingsThe Electron auth window, the token paste fallback, and conflict handling when the same note is edited on two devices.
  6. Theming and Omarchy bridgeMap the current Omarchy theme onto a LatteWrite style object; ship a handful of Scriptorium-native themes alongside.
  7. The Omarchy pluginBar widget plus overlay, on the omarchy-emulatte manifest pattern: note count and sync state in the bar, a fuzzy note-search overlay, and quick-capture straight into a new note.
VII

Where it stands

All seven phases are built, and sync is now verified against the real account: 203 live notes, pulled by the packaged AppImage.

Getting there took one real bug, worth recording because it will happen again in another Electron project here. electron-vite externalises runtime dependencies, so import createClient from 'simperium' compiled to a bare require("simperium") with no interop helper. node-simperium is Babel-compiled CommonJS whose factory sits on .default, so that bound the namespace object rather than the function, and sync.start() threw on its first line at every launch. It hid well: the throw landed inside a whenReady handler and an IPC handler, both of which swallow it into a rejected promise, so the app looked healthy while the feature was dead. The token had been captured correctly the whole time.

The lesson is narrower than "check your imports": verify interop through the path the app actually uses. A scratch require() proves nothing, because require honours __esModule, native ESM does not, and the bundler is a third answer again.

Two notes on how the rulings were implemented. "Drop images" is implemented as no way to insert one, while existing ![alt](url) syntax in a note is still parsed and written back intact, because eating it on open would be the same data loss this design exists to prevent. And "remove the destructive features" is enforced by the test suite, not just by the toolbar: the schema audit fails the build if colour, highlight, FX or font marks ever reappear.

The app is at ~/Documents/DEVELOPMENT/CLAUDE/Scriptorium and the plugin at ~/Documents/DEVELOPMENT/CLAUDE/omarchy-scriptorium, both committed. The AppImage is installed at ~/Apps/Scriptorium/Scriptorium.AppImage, deliberately not in dist/: settings live beside the binary, so shipping from a build-output directory would destroy the signed-in token on the next build.
